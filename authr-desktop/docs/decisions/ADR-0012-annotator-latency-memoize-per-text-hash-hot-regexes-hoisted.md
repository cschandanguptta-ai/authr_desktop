# ADR-0012 — Annotator latency: memoize per text-hash, hoist hot regexes; the echo "cap" is measurably unnecessary

**Status:** Accepted (post-P5 maintenance slice, 2026-11-11)
**Context:** Tech-debt D-08 flagged the regex validators' scaling: "cue-regex scanning is O(text) per check and the echo detector is O(n·window); chapters far beyond the 1,000–2,000-word envelope (e.g. 20k words) will feel slow in the annotator path", with the prescribed fix "cap or window the echo scan; memoize per text-hash". The margin rail recomposes on every UI state change and re-ran the full scan on unchanged text each time. Baseline, measured on the sandbox (JDK 21, 2026-11-11, `scripts/latency_probe.kt` via `scripts/p6_probe.sh`): 2,000-word chapter — annotate 55/65 ms (two runs); 20,000-word chapter — annotate 480/484 ms, echo-only 15 ms, cliché-matrix scan 399 ms (83% of the cost). The echo detector was never the bottleneck.
**Decision:** (1) `LiveAstAnnotator.annotate` memoizes the annotation list per (text hash, lorebook hash) in a bounded LRU (32 entries, thread-safe; compute outside the lock; refusals never cached). A rail recomposition on unchanged text is a cache hit returning the **same immutable list instance**; any edit changes the text hash and misses. Measured post-fix: warm repeat <1 ms at both sizes (≈500× on the 20k-word path); cold 20k ≈ 358–443 ms. (2) The echo loop's `[^\w\s]` regex and the POV regexes are hoisted to compiled vals (the loop recompiled a regex per 5-word window). (3) `ClicheCleaner.scan`'s span-dedupe checks only the last kept span (provably equivalent: kept spans are sorted by start, non-overlapping, so the last carries the maximum end) — worst-case quadratic dedupe gone. (4) The debt's **"cap or window the echo scan" option is rejected as unnecessary**: the echo scan measured 15–17 ms at 10× the envelope; a cap would sacrifice determinism for nothing. The 154-pattern cold scan stays as-is — it is the deterministic gate that decides what ships (hard rule 5: guardrails stay local), it runs once per confirmation, and the cold numbers are within one-shot tolerance.
**Alternatives considered:** word-count cap on the echo scan (rejected — measured unnecessary, changes behavior beyond the envelope for no perceived gain); parallelizing the 154-pattern scan across threads (rejected — nondeterministic ordering risk for ~0.4 s saved once per confirmation); caching by string identity instead of content hash (rejected — the rail passes equal-content strings from recomposition, identity is unstable across rebuilds).
**Consequences:** The annotator carries a process-wide cache; its key includes the lorebook fingerprint, so lore edits miss correctly (test-guarded). Memory is bounded at 32 chapters' annotation lists. Cold scans of 20k-word chapters remain ~0.4 s — acceptable for an explicit confirm action, not a per-keystroke path.
**Do not change unless:** the rail starts calling `annotate` per keystroke (then revisit the cold path, not the cache).
**Evidence:** `engine/LiveAstAnnotator.kt` (cache + hoisted regexes), `engine/ClicheCleaner.kt` (O(1) dedupe), `AnnotatorPerfTest` (9 guards incl. latency ceilings), `PrintInteriorTest` unchanged behavior via golden corpus 1.0000, probe numbers above and in `docs/tech-debt.md` D-08.
